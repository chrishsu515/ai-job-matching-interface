# 畫面設計與實際驗收

採 frontend-design（網頁設計技能）與 web-visual-redesign-review（網頁畫面驗收技能），設計為「證據核對工作台」。工作台直接輸入，沒有大型行銷區、整體分數或難解釋的儀表板。

視覺層級依序是職缺／必要條件、判斷／履歷證據、完整原文與費用。桌面理由與來源採約 60：40；手機單欄，來源完整展開。原文、模型提案及使用者修正都有文字標籤，不以顏色單獨區別。缺少證據用中性色；待確認為褐色；失敗／阻擋才用紅色。

內文 16px、輔助文字 14px，段落行高 1.6 以上。主要觸控目標至少 44px，標籤與輸入對應。英文及技術名稱保持單字完整，長路徑與資料預覽僅在局部捲動，不造成整頁溢出。

已用系統 Chrome（實際瀏覽器）完成合成與真實模型操作，檢視 1440／768／390／320px 截圖：條件主次清楚、來源區隔足夠、沒有文字重疊或整頁水平溢出。320px 是瀏覽器尺寸模擬，不是手機實機。

對話框使用原生 dialog（模態對話框），限制焦點、Escape（關閉鍵）可關閉，回復開啟按鈕的焦點。鍵盤可到輸入、核對、引用、分析、接受、拒絕及還原；載入與成功透過狀態播報。尚未確認、過期、空資料、錯誤與取消都有實際呈現及截圖。

200% 顯示縮放與 prefers-reduced-motion（減少動畫偏好）已檢查。axe-core（自動無障礙掃描）在四個尺寸的分析頁未發現違規；這不等於所有 WCAG（無障礙規範）人工項目完整認證。Safari、手機實機及螢幕閱讀器未驗收。

電腦操作工具啟動時回報核心資源路徑不存在，已依方案使用 Playwright（瀏覽器自動化）搭配系統 Chrome。證據見 evidence/browser（瀏覽器截圖及掃描資料），真實結果與影片另列，不將固定範例當成模型完成證據。

## 2026-10-07 整批比對流程

前一版依每張卡片顯示不同下一步，未能讓使用者看出一份履歷與整份職缺清單的關係。現行主流程是確認一次履歷，由系統依序整理並比對全部職缺；所有卡片提供一致的「查看比對結果」入口。首頁需清楚呈現目前選用的履歷、整批進度與結果數；補充經歷／作品來源歸在履歷區。結果頁明確區分原文、模型提案及人工修訂，並標示職缺條件尚未人工確認的狀態。

系統 Chrome（瀏覽器）實際截圖確認 1440／768／390／320px 無水平溢出；整批區間距 24px，三步在手機依序單欄，44px 主要操作目標，狀態有文字標示而非只靠顏色。已操作鍵盤完整流程及四尺寸無障礙掃描；外部設計平台及獨立人類可用性研究未執行，不提供平台評分或訪談結論。證據見 evidence/browser/batch-home-*（固定模式整批畫面）與 evidence/batch-workflow（真實整批）。
